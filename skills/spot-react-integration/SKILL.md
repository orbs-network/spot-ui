# Spot React Integration

Implement the requested Spot behavior inside the host application. These are instructions for the agent, including when the user relies on AI to make technical decisions. Discover the host's architecture and installed API before asking questions; keep questions to unresolved product choices or external partner activation. Create missing trading services when the host has no DEX infrastructure.

## Discover and choose the narrow path

Prefer the installed version-matched skill at `node_modules/@orbs-network/spot-react/dist/integration-skill/SKILL.md`; verify its `manifest.json.sdkVersion` matches the installed package version. Read [Quickstart](references/01-quickstart.md), then inspect the manifest/lockfile, installed exports/types and peer versions, wallet adapter, swap state/quotes, component tree, chain/token metadata, and partner evidence. Use that evidence to choose:

- **No DEX or missing trading services:** read [Starting without a DEX](references/08-starting-without-dex.md) before provider setup. Build only the missing wallet, network/token registry, balances, quote/price resources, and UI needed by the requested features. Keep an existing app's stack; scaffold a minimal app only when none exists.
- **Existing router/source only:** use the client's public preparation/signing/submission flow without adding a provider or rebuilding the form. Read [Swap and migration](references/07-swap-and-migration.md), verify installed declarations, and adapt the existing host wallet flow.
- **Swaps:** use public client APIs without a provider, plus host state and optional `swap-ui` presentation. Read [Swap and migration](references/07-swap-and-migration.md).
- **Advanced React form or tabs:** wire `AdvancedOrdersProvider` to host state for the requested TWAP, Limit, Stop-Loss, or Take-Profit modules. Read [Provider](references/02-provider.md) and relevant [Panels](references/03-panels.md). `OrderType` contains only `TWAP`, `LIMIT`, `STOP_LOSS`, and `TAKE_PROFIT`.
- **Advanced orders:** add the requested price/schedule controls and validation; use the relevant panel sections and [Integration principles](references/04-principles.md).
- **History/cancellation:** load the history sections of [Panels](references/03-panels.md) only when that surface is requested. Keep it inside the provider or a context-preserving portal.
- **Liquidity Hub migration:** read [Swap and migration](references/07-swap-and-migration.md) and replace the old quote/spender/signature/execution contract; legacy payloads cannot be submitted as Spot orders.

Load [UI references](references/05-ui-reference.md) and [Tooltip copy](references/06-tooltips.md) when implementing those visual controls; do not load every reference for a narrow task. Adapt the [form skeleton](assets/spot-form-skeleton.tsx) only after checking its imports against the installed versions. The [reference implementation](https://github.com/orbs-network/spot-ui/blob/master/apps/web/components/spot/spot-form.tsx) shows one complete host integration, not mandatory scope for every request.

## Integration invariants

- Protocol quotes and orders use ERC-20 input addresses. The React advanced provider uses its host `WalletInteractions` contract for confirmed wallet operations and verifies allowance after approval receipts. Provider-free swaps use DEX wallet services directly; the core SDK takes no wallet adapter. Read allowance before wrapping, confirm receipts, and ensure allowance covers the exact input. `ApprovalRequest.approvalAmount` is a suggested cap; hosts may approve the exact required `amount` or apply their policy. Prepare after prerequisites and preserve original signing bytes.

- Use public root exports from the installed `@orbs-network/spot-react`. It depends on `spot-ui` and re-exports SDK helpers; a separate core install is unnecessary. Verify the installed API and React peer compatibility before adding/changing packages. Do not blindly install `@latest`, duplicate existing wallet/state/numeric libraries, or import private source/`dist/*` paths. A new host still needs wallet/read capabilities; choose compatible dependencies only for missing services.
- Reuse existing navigation, amount inputs, token selectors, dialogs, formatting, translations, and design-system primitives. Add only missing local controls needed by the requested modules. Use the existing progress UI where suitable; when adopting the documented `@orbs-network/swap-ui` flow, verify its installed exports and adapt its appearance to the DEX.
- Keep tokens, typed amount, balances, quote lifecycle, connected account/chain, and wrapped-native/explorer metadata in the host's source state. Pass stable objects/functions directly to `AdvancedOrdersProvider`; use a small DEX-owned adapter context only where multiple components need it. Avoid mirrored calculated state or a second global store.
- Let the provider initialize its client and protocol configuration. The host selects the real partner/chain; never invent configuration, use another DEX's partner, or hard-code contracts. Missing activation should produce a sanitized support draft and unavailable submission while independent work continues.
- Supply one localized `errorFallback` for initialization and calculation/rendering failures. `SpotErrorFallbackProps` contains `error: Error`, `retry: () => Promise<void>`, and `isRetrying: boolean`. Initialization errors keep children mounted beside the fallback; retry refetches configuration. Rendering retry resets the boundary.
- Adapt the host wallet through the installed `walletInteractions` contract. Write methods wait for successful receipts; signing receives the SDK signing request and returns the wallet's original signature unchanged. The host's required `shouldWrap`/`shouldApprove` callbacks decide whether writes are needed; false skips the write, while invoked transaction callbacks return confirmed hashes and throw on failure; React normalizes native input to `wrappedNativeToken` for protocol execution. Spot does not supply a wallet library.
- Import wallet adapter types (`WalletInteractions`, `AllowanceRequest`, and `GetAllowanceProps`) and `WalletInteractionError`/`WalletInteractionErrorCode` from `spot-react`. React wrapping/approval failures preserve `WRAP_FAILED`, `APPROVAL_FAILED`, and `INSUFFICIENT_ALLOWANCE`; these are outside the core `SpotErrorCode` union. Core `Eip712TypedData`, `OrderSigningRequest`, and `ApprovalRequest` remain public preparation data for direct DEX signing and are re-exported by React.
- Read the authoritative form through `useOrderForm()` and focused public hooks such as `useTrades`, `useLimitPrice`, and `useOutputAmount`. Keep host balance policy and returned validation visible. Preserve explicit TWAP trade selections across amount edits and render `MAX_TRADES` rather than silently clamping them.
- Quote amounts describe the complete typed input and current pair/chain/partner. Withhold stale values while replacing requests. Advanced forms receive a plain `MarketQuote` with only optional `quotedOutputAmountRaw`, `isLoading`, and `noLiquidity`; pass token USD prices separately. If quoting through the SDK, map its current `netAmountOut` in the host adapter. Provider-free swaps pass their original reviewed `SwapQuote` directly to the client; never apply slippage again.
- Use `useExecution`/`useSubmitButton` for advanced-provider execution. Prevent duplicate starts for the visible attempt, pause obsolete quotes during its execution, and keep review/progress scoped to the captured attempt. `startNewOrder()` may detach active or unconfirmed execution and release the visible form while retaining the original attempt; captured callbacks and history updates continue while the provider stays mounted. Advanced creation succeeds at acceptance; `order-completed` keeps submission disabled until an explicit new-order reset. Provider-free swaps keep host loading state through their wallet flow and status polling, and succeed only after a fill. `checkOrderStatus()` reconciles retained attempts without resubmission; absent history and service outages remain uncertain even after expiry. Keep background recovery visible with `hasUnconfirmedExecutions` and disable its action during `isCheckingOrderStatus`.
- Without a provider, confirm host wrapping/approval, call `client.prepareSwap({ quote, account, signal })` or `client.prepareOrder({ form, account, inputTokenAddress, outputTokenAddress })`, sign the returned EIP-712 data inline, and submit the exact order/original signature through `client.submitSwap` for swaps or `client.submitOrder` for advanced orders. Both return acceptance. The core SDK has no execution factories, wallet adapters, or session/progress types.
- For provider-free routers, retain host scope checks, receipt confirmation, progress, retries, and duplicate guards. `prepareSwap()` reuses quotes aged zero to 20 seconds inclusive or refreshes the same request; a refreshed minimum below the reviewed floor requires fresh review. Freeze `prepared.quote` before signing. Preserve prepared order, original signature, confirmed hashes, and accepted/latest order, and reconcile uncertain POST responses before a replacement or fallback. Configure reporting only through `createClient(..., { disableAnalytics })` options.
- For provider-free UI previews, read wrapping requirements and allowance through DEX wallet services. Keep the review button disabled with a loader during pending allowance reads; verify allowance after confirmed approvals. Show swaps as complete only when host status polling observes `OrderStatus.Completed`.
- Refresh host balances from lifecycle callbacks (`onWrapSuccess`, `onOrderCreated`, `onOrderFilled`, progress, cancellation) supported by the installed version. Keep input on failure/rejection. Clear the host input after success, or when an explicit new-order action successfully calls `startNewOrder()` for an active or unconfirmed attempt. `returnToOrderForm()` rejects active/unconfirmed resets; `startNewOrder()` rejects stale callbacks. Form resets clear visible wrap snapshots; never treat a receipt as current spendable balance. Intentional account/chain/partner changes quietly dismiss wallet work before submission while preserving uncertain or accepted orders. Keep the provider mounted for background callbacks.
- For requested history use `order.historyKey`, configured SDK fetching, and `useCancelOrder(order)`. Keep transient modal state separate from the provider's execution/history lifetime. Raw amounts are for protocol calls; use the DEX amount type/formatter for display.
- Preserve required disclaimer and tooltip meaning for the implemented controls. Use the maintained English defaults when translations are absent or empty. Keep advanced token selection on the connected chain and render connect/switch-network states when needed.

## Verify and hand off

Run the host's available build/typechecks and relevant existing checks, then verify the changed UI in a browser when available. Check loading/config errors, validation, requested module navigation, review/progress behavior, and history only if included. Keep verification read-only unless live wallet execution is explicitly authorized. Respect the host user's constraints on new files and tests; prefer relevant existing checks.

Report what works, what was actually verified, and a specific remaining blocker/action in plain language. Prepare a ready-to-forward, sanitized support message for missing partner activation as described in Quickstart; do not send it automatically or leave independent work undone.

Current SDK builds bundle this skill, its references/assets, and a version-stamped manifest under `dist/integration-skill/`. Reading those documentation files is allowed; SDK code imports still use only the public package root. If an older package has no bundled skill, use the [repository skill](https://github.com/orbs-network/spot-ui/tree/master/skills/spot-react-integration) from a matching release/checkout and check `packages/spot-react/package.json`; do not assume repository main matches the installed release.
